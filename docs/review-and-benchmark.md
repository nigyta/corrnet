# コードレビュー・実装調査・ベンチマーク報告

対象：`0337429`（multithreading）から `perf/merge` までの変更
作成日：2026-10-01

## 1. 概要

corrnet のコードレビューを行い、既存の論文や実装と照らし合わせて共発現の順位の定義を確かめました。その結果を受けて、正しさの修正と高速化を行いました。

- **正しさ**
  - 順位付けに不具合があり、負の相関を持つ遺伝子が正の相関を持つ遺伝子の順位を押し下げていました。
  - MBEX 論文とその引用元の定義である「符号付き PCC の降順・自分自身は 0」に修正しました。
- **速度**
  - 検証データ（17,939 遺伝子 × 460 サンプル）で使用例の 3 コマンドを続けて実行すると、約 136 秒かかっていたのが約 21 秒になりました。
- **メモリ**
  - `construct` は最大 18.5 GB から 4.3〜4.6 GB に、`merge` は 21〜24 GB から 3.2 GB に減りました。

## 2. 共発現の順位の定義（文献・既存実装の調査）

本ツールは MarpolBase Expression（MBEX；Kawamura et al. 2022, *Plant Cell Physiol*, [doi:10.1093/pcp/pcac129](https://doi.org/10.1093/pcp/pcac129)）で使われています。

### MBEX の方法の節の記載

- 前処理：log2(TPM + 0.25) にしてから PCC を計算します。
- 式：HRR(A,B) = max(rank(PCC(A,B)), rank(PCC(B,A)))、MR(A,B) = √(rank(PCC(A,B)) × rank(PCC(B,A)))。自分自身の順位は 0 です。
- 引用元：Liesecke et al. 2018（[doi:10.1038/s41598-018-29077-3](https://doi.org/10.1038/s41598-018-29077-3)）と ATTED-II v11（Obayashi et al. 2022）です。
- 順位を「符号付き」で付けるのか「絶対値」で付けるのかは、本文には書かれていません。

### 引用元と、その他の文献・実装の定義

いずれも **符号付き PCC の降順** で順位を付けています。|r| で順位を付けるものはありませんでした。

| 出典 | 順位の基準 | 自分自身 | 備考 |
|---|---|---|---|
| Obayashi & Kinoshita 2009（MR の原著、[doi:10.1093/dnares/dsp016](https://doi.org/10.1093/dnares/dsp016)） | 符号付き降順 | — | 「負の PCC はゼロより弱い関係として扱った」と明記 |
| ATTED-II 2018 / v11 | 降順のリストでの順位 | 除外（MR は 1〜遺伝子数−1） | MR が大きいほど負の相関に相当すると説明 |
| Mutwil et al. 2010（HRR、[doi:10.1104/pp.109.145318](https://doi.org/10.1104/pp.109.145318)） | 符号付き降順 | 除外 | HRR ≤ 30 |
| CoNekT / LSTrAP（ソースコード） | 符号付き降順 | 除外 | HRR = max(0 始まりの順位) + 1。両方向とも上位 `limit` 以内でなければ辺を作らない |
| Wisecaver et al. 2017 / MutClust / MutAgg | 符号付き降順 | 実装により異なる | MR ≤ 100、辺の重みは e^{−(MR−1)/N} |

このため corrnet の順位は「**符号付き PCC の降順、自分自身は 0、最良の相手は 1、同点は添字順、NaN は最下位**」としました。

### codon-usage の評価指標

- `cosmix` として実装されていた式は、COXPRESdb/ATTED-II の **COXSIM**（Obayashi et al. 2013, *NAR*, [doi:10.1093/nar/gks1014](https://doi.org/10.1093/nar/gks1014)）と完全に一致します。名前を `coxsim` に改めました。
- 文献では k = 100 か上位 1% を使い、ランダムを 1 とする正規化をしています。corrnet は今も k = 10%（`--percent 0.1`）で、正規化もしていません（未対応）。

## 3. コードレビューの結果

### 修正したもの

| 区分 | 内容 | 場所 |
|---|---|---|
| 不具合（結果が変わる） | 順位付けで、|r| で並べ替えたリストを符号付きの r で検索していた。負の相関はすべて最下位（n−1）になり、正の相関を持つ遺伝子は強い負の相関を持つ遺伝子の数だけ順位が下がっていた | `rank.rs` |
| 不具合（結果が変わる） | 自分自身を除く処理を対角の値（1.0）に頼っていたため、他の遺伝子が r = 1.0 だと順位が崩れた | `rank.rs` |
| 不具合（結果が変わる） | `construct` の `--pcc_cutoff` だけが |r| で判定していた（`extract`/`query` は符号付き）。符号付きに統一した | `graph.rs` → `network.rs` |
| 不具合 | コドンの集計で最後のコドンが数えられず、3 塩基未満の配列ではパニックした | `codon.rs` |
| 不具合 | codon-usage で近傍が k 個未満の遺伝子があるとパニックした。警告を出してスキップするようにした | `handlers/codon_usage.rs` |
| 不具合 | `--log DEBUG` で遺伝子が 5 個未満だとパニックした | `handlers/construct.rs` |
| 不具合 | merge の結合キー `"gene_1-gene_2"` が、名前に `-` を含む遺伝子で衝突した（`a-b,c` と `a,b-c`） | `handlers/merge.rs` |
| 不具合 | merge が gzip の入力を読めなかった（polars 0.17） | `handlers/merge.rs` |
| 未定義動作 | `matrixmultiply` 0.3.2 は ARM 上で、スレッドローカルのバッファの配置がずれていた。0.3.11 に更新した | `Cargo.lock` |
| 速度 | COXSIM の計算量が O(k²) だった。O(k) にした | `similarity.rs` |
| 速度 | codon-usage が並列処理の中で Mutex のロックを取っており、実質 1 本ずつ順番に動いていた | `handlers/codon_usage.rs` |
| 速度・メモリ | 相関の計算が 1 スレッドだった。行のまとまりごとに並列で行列積を計算するようにした | `math.rs` |
| 速度・メモリ | 全辺（1.6 億本）を `Graph` に溜めた上で複製し、1 辺ごとに String を確保していた。その場で書き出す方式にし、順位は u32 で持つようにした | `network.rs` |
| 速度・メモリ | merge が polars で 2 つのファイルを丸ごと読み込んでいた。並列で流し読みするハッシュ結合にし、polars を依存から外した（依存パッケージ 170 → 123） | `handlers/merge.rs` |

### 未対応のもの

- `query`
  - 出力先が `test` という名前に固定されている。
  - `depth > 1` では何も出力しない。
  - `dfs` の `map.get(query)` は `map.get(k)` の誤りで、訪れた遺伝子も記録していない。
- `extract`：1 レコードごとに String を確保している。`from_utf8_unchecked` は、UTF-8 でない入力が来ると未定義動作になる。
- `read_exp_csv`：数値でない値があると `expect` でパニックする。`--log2` で負の値があると、何も言わずに NaN になる。
- 前処理
  - 擬似カウントの既定値は 1 のまま（MBEX は 0.25 で、使用例では `--pseudocount 0.25` を指定している）。
  - 低発現遺伝子を除くフィルタがない。
- COXSIM：k の既定値と正規化が文献と違う。
- 未実装：todo.md にある logit score（LS = log₂(N − MR) − log₂(MR)、ATTED-II v11）と HCCA。
- 依存のバージョン指定に `*` が残っている（`bio`, `itertools`, `approx`, `num-traits`）。テストを実行する CI がない。

## 4. 挙動の変更点（旧版との互換性）

- **`construct` の順位が変わる**：符号付きの定義に修正したためです（2 章）。
  - 旧版で閾値を満たした辺は、すべて新版でも満たします。新版では辺が増える方向にだけ変わります（6 章）。
- **`construct --pcc_cutoff` は符号付きで判定する**：負の相関の辺は閾値を満たさなくなります。
- **`merge`**
  - 出力は旧版（polars）とバイト単位で一致します。行の順序は、旧版と同じく優先しない側のファイルの順序です。
  - gzip の入力が使えるようになりました。
  - 名前に `-` を含む遺伝子の結合を誤らなくなりました。
  - 同じ辺が 2 回出てくる入力はエラーにします。
  - `.gz` 出力は、並列に圧縮した gzip メンバーを連結した形式です。`gzip`、`zcat`、Python の `gzip` で読めます。旧版よりファイルが 0.05% 大きくなります。
- **`codon-usage`**：近傍が k 個未満の遺伝子は、パニックせずスキップします。

## 5. ベンチマーク

### 測定条件

- マシン：Apple M4 Pro（14 コア）、メモリ 48 GB、macOS
- データ：`data/gene_tpm.csv`（17,939 遺伝子 × 460 サンプル、68 MB）
- 辺の数：1 ネットワークあたり 160,894,891 本。出力は MR 9.4 GB、HRR 7.3 GB
- 各コマンドは 1 つずつ順番に実行しました。時間とメモリは `/usr/bin/time -l` の real と maximum resident set size です

```sh
corrnet construct --pseudocount 0.25 --log2 --method MR  --input gene_tpm.csv --output rank_MR.csv
corrnet construct --pseudocount 0.25 --log2 --method HRR --input gene_tpm.csv --output rank_HRR.csv
corrnet merge --hrr rank_HRR.csv --mr rank_MR.csv --priority MR --outpath rank_MR_HRR_merged.csv
```

### 全体の比較

| コマンド | 旧版 `0337429` | 新版 |
|---|---|---|
| construct MR | 49.2 秒 | **5.6 秒 / 4.6 GB** |
| construct HRR | 32.1〜36.2 秒 / 18.5 GB | **3.3 秒 / 4.3 GB** |
| merge（`.csv` 出力） | 43.0〜50.6 秒 / 17.8〜21.5 GB | **11.9 秒 / 3.2 GB** |
| merge（`.csv.gz` 出力） | 62.5 秒 / 24.3 GB | **15.2 秒 / 3.2 GB** |
| merge（`--priority HRR --max-rank 100`） | 38.9 秒 / 21.1 GB | **6.0 秒 / 0.34 GB** |
| 3 コマンドの合計 | 約 136 秒 | **約 21 秒** |

- 旧版の construct MR の最大メモリは、計測時のメモリ圧縮の影響で正しく測れなかったため省きました。HRR と同程度と考えられます。
- merge の旧版の値の一部は、新版の construct の出力を入力にして測りました。merge のコードは旧版と同じです。

### construct HRR の段階ごとの時間（ログのタイムスタンプから）

| 段階 | 旧版 | 新版 |
|---|---|---|
| CSV の読み込み | 0.1 秒 | 0.1 秒 |
| log2 変換と相関の計算 | 11.8 秒 | 0.7 秒 |
| 順位行列の計算 | 2.2 秒 | 0.7 秒 |
| 辺の作成と CSV 書き出し | 19.2 秒 | 1.7〜2.6 秒 |

### 列（サンプル）が 4 倍になった場合（17,939 遺伝子 × 1,840 サンプル、合成データ）

| | 460 列 | 1,840 列 |
|---|---|---|
| construct HRR | 3.5 秒 / 4.3 GB | 6.1 秒 / 4.7 GB |
| construct MR | 4.6 秒 / 4.6 GB | 7.2 秒 / 5.1 GB |
| うち読み込み + 相関の計算 | 0.15 + 0.71 秒 | 0.57 + 3.29 秒 |

- 列数に比例して増えるのは、読み込みと相関の計算だけです。順位付けと辺の書き出しは遺伝子数だけで決まります。
- 最大メモリは、おおよそ **12·n² バイト ＋ 16·n·m バイト ＋ 約 0.4 GB** です（n は遺伝子数、m はサンプル数）。
- merge は辺のリストだけを読むので、列数には直接関係しません。

## 6. 正しさの検証

- **参照実装との比較**
  - 定義をそのまま numpy で書いた参照実装と、新版の出力を比べました。対象はランダムに選んだ 40 遺伝子が関わる 716,740 辺です。
  - 完全には一致しない辺（HRR 274 本、MR 426 本）は、すべて相関が数値的に同じ値になる遺伝子のグループ（最大 15 遺伝子）の中での並び順の違いでした。許容誤差 1e-12 で同点とみなせば、範囲から外れる辺は 0 本です。
  - 10 遺伝子と 400 遺伝子（合成データ）では、完全に一致しました。
- **各段階での出力の一致**
  - 辺の書き出し方式の変更：変更前とバイト単位で一致しました。
  - 相関の計算の並列化：相関の差は最大 2.1e-14 でした。順位が変わった辺は全体の約 0.1% で、すべて同点グループの中です。
  - merge の書き直し：全データで、旧版とバイト単位で一致しました。2 つのファイルの行の順序が違う入力、引用符が必要な遺伝子名、gzip 出力でも一致しました。
- **ネットワークの変化（旧版 → 新版）**
  - 旧版で閾値を満たす辺は、すべて新版に含まれます。
  - 新版の MR ≤ 100 と HRR ≤ 100 の辺に、負の相関の辺は 1 本もありません。

| 閾値 | 旧版 | 新版 | 重なり（Jaccard 係数） |
|---|---|---|---|
| MR ≤ 30 | 163,941 | 165,990 | 0.988 |
| MR ≤ 100 | 645,214 | 656,658 | 0.983 |
| MR ≤ 1000 | 7,658,492 | 8,145,769 | 0.940 |
| HRR ≤ 30 | 79,174 | 80,308 | 0.986 |

| HRR ≤ 1000 | 4,690,615 | 4,938,313 | 0.950 |

- **x86_64（AMD64）での確認**
  - Rosetta 2（SSE2 のカーネル）：テストはすべて通りました（11 回中 11 回）。全データで ARM 版と比べると、相関の差は最大 1.4e-14、順位が変わった辺は 0.03〜0.05% で、すべて同点グループの中です。
  - Docker の linux/amd64（glibc、AVX2/FMA のカーネル）：テストはすべて通りました（6 回中 6 回）。3,000 遺伝子のデータで、順位は完全に一致し、相関の差は最大 6.7e-16 でした。
  - まだ確認していないこと：実機の AMD CPU での速度、AVX-512 版のカーネル、musl 版のバイナリの速度。Linux では glibc 版（`x86_64-unknown-linux-gnu`）を推奨します。
- **テスト**：`cargo test` は 22 件すべて通りました。clippy の警告は 17 件から 13 件に減りました。

## 7. 注意事項

- 相関が数値的に同じ値になる遺伝子のグループ（低発現の遺伝子に多い）の中では、計算環境によって順位が入れ替わることがあります。そのため、環境が違うと出力がバイト単位で一致するとは限りません。
- 遺伝子数が増えると、メモリと時間は遺伝子数の 2 乗で増えます。たとえば 3 万遺伝子なら、相関行列と順位行列だけで約 10.8 GB になります。
- 使うスレッド数は `RAYON_NUM_THREADS` で指定できます（何も指定しなければ全論理コアを使います）。
